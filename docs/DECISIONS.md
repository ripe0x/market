# Decisions

## Unified action protocol superseding decisions, 2026-11-19

The owner specified a single model: every order is an order for an authorized contract action. Ordinary NFT sales, bids, transferable actions and reserved artwork operations use one account implementation, one action interface and one execution lifecycle. This section supersedes D401–D415 and the order-only handler decisions wherever they conflict. Earlier entries remain as history; the deployed Sepolia contracts still run the code those entries describe.

| ID | Decision | Why and superseded boundary |
| --- | --- | --- |
| D501 | `Market`, `Order` and `Actions` form the core. `Order` is the only account implementation; `IAction` (`validate`, `onExecute`, `onRelease`) is the only implementation interface; `Order.execute(input)` is the only execution entrypoint. `Right`, `Rights`, `IOrderHandler`, `IExerciseHandler`, `fill` and `exercise` are removed. | One lifecycle (Pending, Live, one terminal state) and one authority model for every action. Admission (Public or Holder) replaces the old order/right split: Public orders are cancelable immediate offers, Holder orders are transferable commitments the issuer cannot cancel. |
| D502 | The full configuration, issuer, action, action runtime code hash, admission, deadline and residual are appended to the clone's code and read back by `Order`. `config()` stays readable after termination and token burn. Configs longer than a clone's code limit revert in `Clones`. | Recovery and authentication must not depend on events or an indexer. Supersedes storing only a config hash and passing config to `fill`. |
| D503 | One shared `ExchangeAction` handles ordinary ERC721 sales and bids, selected by immutable config. The trading fee is snapshotted at activation, bounded by the issuer's `maxFeeBps`, and stored as activation terms; the recipient is read once per execution. `FeeConfig` keeps two-step admin, a current rate and recipient, and drops the rate history and its Market dependency. | Supersedes `NFTSale`/`NFTBid` (D407) and the creation-time rate lookup (D306, D309, O4's "rate in force when created"). The 1% cap, the separate admin and the fee recipient are unchanged. The rate a seller accepts is now visible as a bound in the order and fixed at activation. |
| D504 | Incoming bid NFTs are approved to `ExchangeAction`, which pulls only the authenticated executing actor's named token during a validated execution. Orders never hold or use NFT approvals for bids. No issuer or residual can make arbitrary calls as an order. | A regression (test/BidApproval.t.sol) shows an approval to an Order is exploitable through native withdrawal to a collection that acts on its caller's identity, and through a proceeds receiver during execution. Retains the A1 rule. Supersedes the old owner `execute` recovery of closed orders (D003, D008, O6's generic recovery). |
| D505 | Royalty remains capped at `price - fee` and the trade settles; a reverting lookup or a nonzero royalty with no receiver reverts. The sale `maxRoyaltyBps` applies to the capped amount. | Owner-approved O5 and D308 ("having a high royalty brick it is not acceptable"). The new specification asks that royalty and fee stay within the price; the cap satisfies that without changing O5. |
| D506 | `Order.release(recipient, input)` asks the action to clean up backing while the order is Pending or terminal. Only the residual may choose a recipient other than itself. Each action decides who may trigger cleanup: asset delivery (sale escrow, covered collateral) requires the residual itself; reservation cleanup of an ended order is permissionless. Release calls carry no ETH. Native surplus is withdrawn separately by the residual and never touches credits. | Separates terminal transitions from cleanup so a failing recipient or broken target never blocks termination, and avoids a generic rescue call. Unknown assets or a broken custom action can remain unrecoverable. |
| D507 | `IReservedActionTarget` is this project's proposed interface. One permanent reservation per executor per target; a scope holds one live reservation; old cleanup never clears a newer grant. `ReservedAction` lets only the residual release a Pending order's reservation. | A stranger could otherwise void a reservation between creation and activation, permanently burning that executor address. The target's own clock governs expiry. |
| D508 | `CoveredNFTPurchase` rejects canonical Actions tokens as collateral; a rejected Pending setup stays recoverable by the residual without rechecking activation policy. | An Actions token can expire independently, so it cannot back a promise of future delivery. |
| D509 | `AcquireAndExecute` receives the Actions token and executes as its owner. It spends only the current call's ETH, refunds the unused part, and leaves any preexisting balance untouched. | Atomic purchase without operator execution, actor impersonation or arbitrary calls. |
| D510 | Ordinary NFT trades require `minActionTimeLeft == 0`; the contract rejects nonzero values for ordinary collections. Actions token bids must name a token; their minimum lifetime is the bidder's term, a sale's is the purchaser's input. | Prevents a meaningless lifetime requirement on ordinary NFTs and keeps action eligibility checked against live chain state. |
| D511 | `Order` accepts ETH and ERC721 receipts only; ERC1155 hooks are removed. `PaintAction`, `ReservedPaint` and the painter role are removed; `Artwork` demonstrates palette and renderer reservations. `FillVerifier` is kept. | The supported scope is native ETH and ERC721. The revocable immediate painter example is replaced by the reservation example on the same lifecycle. |
| D512 | `Market.create` accepts a deadline at or before now; only `activate` rejects it. `BadDeadline` is removed. Every check in `create` must stay independent of time and chain state. | `createAndActivate` invites sending backing to the predicted address first. With the old check, a seller whose second transaction landed after the deadline could never deploy that address and the NFT or ETH there was stranded permanently (reproduced in `test/ListingRecovery.t.sol` before the change). Now the late order is created Pending and expired, never activates, and the residual releases the backing. Cost: anyone can create born-expired orders, which is no worse than creating orders that are never activated. Changes Market bytecode and every address that depends on it; FeeConfig and FillVerifier are unchanged. A one-transaction ERC721 listing hook on Market was considered and deferred as a product feature with new core surface. |

## Transferable rights superseding decisions, 2026-11-17

The owner approved a core architecture change: a transferable right is a different protocol object from a cancelable order. This section supersedes the order-only scope of D001, D003, D005, D008, D010, D012 and D014 **for rights only**. Those historical choices and the ordinary order implementation remain in place. The complete pre-implementation rationale and state table are in [RIGHTS_DESIGN.md](RIGHTS_DESIGN.md).

| ID | Decision | Why and superseded boundary |
| --- | --- | --- |
| D401 | `Market` creates a separate isolated `Right` clone; `Rights` is its canonical ERC721 ownership interface. The token ID identifies the backing account. | A cancelable `Order` cannot guarantee a buyer that the issuer will not close and recover backing. Ownership follows `Rights.ownerOf`, never a second holder field. Isolation preserves per-account custody. |
| D402 | Creation enters pending setup without generic account execution. The issuer supplies assets or a target reservation from outside; handler validation and stored activation terms precede minting. Cancellation of pending setup is permanent. | A transferable token for an empty account is a false claim. Unrestricted setup execution could plant surviving approvals or authority. This intentionally adds activation for rights, superseding D005's no-hook choice for orders. |
| D403 | Active rights cannot be closed or recovered by an issuer. Only the current token owner may exercise or surrender. The bound handler alone acts through the account during an authorized exercise. Successful exercise burns the token and terminates the right. | D003 and D008 gave a fixed order owner cancellation and recovery; those powers would defeat a sold right. No issuer shortcut returns if the issuer buys back the token. |
| D404 | Deadline zero is perpetual. Otherwise `timestamp >= deadline` immediately stops exercise and transfer; anyone can finalize expiry of a pending or active account and enable committed residual recovery. | Finalization need not be timely to protect a buyer. An abandoned pending setup must not strand its backing if the issuer disappears. This is different from an order owner's voluntary close or a handler's own expiry schedule. |
| D405 | The committed residual beneficiary controls generic terminal recovery, with ETH credits reserved first. Exercise beneficiaries pull credits to a chosen destination. | Recovery must survive a broken handler and a rejecting payee without letting the residual beneficiary steal another party's proceeds. Cancellation, surrender, expiry and exercise share this terminal rule. |
| D406 | The supported covered NFT right requires actual NFT custody and fixes the exercise price and ERC2981 recipient and amount at activation, subject to the issuer's limit. Exercise requires exact ETH, verifies delivery and credits the committed split. | Mutable royalty settings or a refusing receiver must not reprice or veto an already sold right. Trading `FeeConfig` remains in the trading layer and does not affect exercise. Direct `NFTSale` royalty and fee rules are unchanged. |
| D407 | `NFTSale` may escrow and resell canonical right tokens. `NFTBid` accepts only a named canonical token ID; collection-wide rights bids are refused. | A sale listing is cancelable separately from the right and does not reset its deadline. Different token IDs in one rights collection can have unrelated value. The rights collection advertises no ERC2981 royalty, so right-token premiums do not automatically pay the underlying NFT's royalty. |
| D408 | `Artwork` supports a target-enforced reservation that survives transfer and cannot be revoked or replaced while live. The right promises one permitted modification, not permanent visual control. Existing `PaintAction` remains a revocable immediate order example. | The old painter role disappeared on artwork transfer and could be revoked, so it cannot back a prepaid transferable right. The external target, not a Market-only check, must enforce durability. |
| D409 | Existing direct NFT sale and bid payouts remain O1–O5, while the right-enabled build changes their gas costs slightly. On the pinned fork, a listing create is 117,761 versus 117,414 gas and a funded bid create 118,152 versus 117,805; an Azuki sale fill is 187,515 versus 187,358 and bid fill 154,852 versus 154,608. | This supersedes the old gas figures in O9 for the new build, without changing the approved 1% fee or royalty destinations. Right-token eligibility checks and changed constructor code account for the additional work. See current snapshots and STATUS.md. |
| D410 | The covered NFT purchase handler activates only if the account's immutable residual beneficiary equals its immutable issuer. The core retains configurable residual beneficiaries for other handlers. | Supersedes the initial supported-handler allowance for a buyer to be both holder and residual. That buyer could surrender or wait for expiry and take the NFT for zero exercise payment. The issuer can still surrender while holding or after buying back the token and recover its own collateral. Only successful exercise allocates the fixed exercise royalty; ERC2981 does not enforce every economic transfer. |
| D411 | Anyone may call `releaseCredit(beneficiary)` to pay only that recorded beneficiary. The existing `withdrawCredit(recipient)` remains beneficiary-only for redirection. Both paths share debit-before-call accounting and revert on payment failure. | Supersedes the original beneficiary-initiated-only payout in D405. A passive accepting receiver must not be trapped merely because it cannot make outbound calls. Exercise remains independent of payout, payment destinations do not change, and no recovery exception or administrator is added. |
| D412 | The canonical `Rights.tokenURI` returns onchain Base64 JSON only while the ERC721 token exists. It identifies the backing account, issuer, exercise handler and its code hash, config hash, activation terms, exclusive deadline policy, residual beneficiary, account state and effective liveness. Deadline zero is labelled perpetual; a finite right at its deadline shows expired and not live even before anyone finalizes it. Burned and pending tokens have no URI. The full handler config remains published in `Market.RightCreated`, not stored again by `Rights`; the URI never calls the handler or an underlying target. | Generic metadata helps wallets and indexers distinguish a transfer from exercise without making the shared ERC721 pretend every right has the same economics. `ownerOf` remains the authoritative holder source, and handler-specific interpretation still requires the committed config and handler code. The initial metadata revision measured `Rights` runtime/initcode from 4,673/5,560 to 7,975/8,862 bytes and `Market` initcode from 16,693 to 19,995 bytes. Measured local direct `CREATE` gas for Market rises from 3,544,290 to 4,259,136 (+714,846); Rights alone rises from 1,154,896 to 1,868,918 (+714,022). These are deployment costs, not per-right custody or exercise fees. It changes CREATE2 deployment addresses; no redesigned contract is deployed. |

| D413 | Metadata emits the uint256 deadline as an exact decimal string and labels the transient exercise window `executing` with `live=false`. | Review of the initial metadata revision found JSON-number rounding above 2^53 and an active label during the local execution lock. A callback collection test reaches the lock and verifies both fields. Final metadata build: Rights runtime/initcode 8,092/8,979 bytes, Market initcode 20,112 bytes. Direct CREATE gas is 4,284,302 for Market and 1,894,047 for Rights, increases of 740,012 and 739,151 over f70294a respectively. |

The redesign intentionally changes Market and handler bytecode and therefore CREATE2 addresses. The 2026-11-16 Sepolia deployment remains historical and does not contain transferable rights. No new contract is deployed by this work.

## Starting point

The earlier work was an NFT selling product: a shared escrow contract holding every listed NFT and bid budget, OpenSea Seaport fills through a zone, fixed protocol and executor fees, a small owner role for currencies and zones, a Next.js app and a keeper. It reached fork tests against real OpenSea offers. Lessons carried over: ETH refunds into EIP-7702 accounts can run out of gas or hit an account without `receive` (here they simply revert the filler's own fill); fee-on-transfer and false-returning tokens must be detected by balance change; and Foundry's via-IR build can cache `block.timestamp` within a test function, so tests use `skip()`.

Nothing else carried over. The new direction removes marketplace semantics, fees, the owner role and shared custody.

### D006: what handler immutability can mean

The goal is that an order is a stable commitment to its execution rules while its application state (price over time, capital, an artwork's colours, a bid's history) changes as those rules allow. What the core can establish depends on what kind of contract the handler is:

| Handler | What the commitment fixes | What can still change behaviour |
| --- | --- | --- |
| Ordinary contract with no upgrade path | The exact bytecode that runs, for the order's life | Only what that bytecode reads: its own storage (written by its own rules) and contracts it calls, such as tokens or the strategy and capital source named in config |
| Upgradeable proxy | The proxy's bytecode, which does not change on upgrade | Everything: whoever controls the implementation pointer controls every bound order during fills |
| Handler that `delegatecall`s an external implementation | The handler's bytecode | Everything the delegate target does, and the target itself if it is chosen from storage |
| Handler that depends on mutable contracts (oracles, admin switches, registries) | The handler's bytecode | Whatever those contracts return; legitimate when it is application state the creator chose, a trust assumption otherwise |
| Code destroyed in its creation transaction and redeployed at the same address (metamorphic) | Detected: fills revert `HandlerCodeChanged`; the owner closes and recovers | Nothing runs |
| EIP-7702 delegated account | Refused at creation | (Its key holder could swap the delegation, or rewrite its storage through another delegate and swap back, at any time) |

A code hash proves only that the bytes executing are the bytes that were readable at creation. Since EIP-6780 a deployed contract's code can change only by being destroyed in the transaction that created it and redeployed, and an EIP-7702 account's code is a pointer its key can change, so the pin and the delegated-account check together make one statement true without qualification: **the code a counterparty reads is the code that will run**. Any way that code's behaviour can change is then visible in it: a `delegatecall`, an admin setter, an external call. Whether that is acceptable is the creator's choice and the counterparty's judgement; Market keeps the choice permissionless.

The reference handlers in `examples/` have no owner, no proxy, no `delegatecall` and no setters. Their only changing inputs are those named in each order's config (tokens, NFT collections, the bid strategy and capital source) and their own per-order state, written only by that order's fills.
