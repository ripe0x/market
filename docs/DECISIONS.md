# Decisions

Each entry records the question, the choice, the alternatives considered and why they lost. Status: **Baseline** (implemented and tested), **Open** (owner review recommended). Entries dated 2026-11-04 unless stated. On 2026-11-05 the owner reviewed the open decisions: D004 changed to clones, D006 and D009 were settled as below, and D003, D005, D007, D008 and D010 to D016 were confirmed. In a second review the same day the owner renamed Policy to OrderHandler (D017), strengthened active-order authority (D003, revised again) and confirmed the handler code pin and delegated-account refusal (D006) for V1. Entries use the new names throughout. This log replaces the decision log of the earlier NFT selling product, which remains on the `claude/market-nft-implementation-d5c4ea` branch.

## Starting point

The earlier work was an NFT selling product: a shared escrow contract holding every listed NFT and bid budget, OpenSea Seaport fills through a zone, fixed protocol and executor fees, a small owner role for currencies and zones, a Next.js app and a keeper. It reached fork tests against real OpenSea offers. Lessons carried over: ETH refunds into EIP-7702 accounts can run out of gas or hit an account without `receive` (here they simply revert the filler's own fill); fee-on-transfer and false-returning tokens must be detected by balance change; and Foundry's via-IR build can cache `block.timestamp` within a test function, so tests use `skip()`.

Nothing else carried over. The new direction removes marketplace semantics, fees, the owner role and shared custody.

### D006: what handler immutability can mean

The goal is that an order is a stable commitment to its execution rules while its application state (price over time, capital, an artwork's colours, a bid's history) changes as those rules allow. What the core can establish depends on what kind of contract the handler is:

| Handler | What the commitment fixes | What can still change behaviour |
| --- | --- | --- |
| Ordinary contract with no upgrade path | The exact bytecode that runs, for the order's life | Only what that bytecode reads: its own storage (written by its own rules) and contracts it calls, such as tokens or the strategy and capital source named in config |
| Upgradeable proxy | The proxy's bytecode, which does not change on upgrade | Everything: whoever controls the implementation pointer controls every bound order during fills |
| Handler that `delegatecall`s an external implementation | The handler's bytecode | Everything the delegate target does, and the target itself if it is chosen from storage |
| Handler that depends on mutable contracts (oracles, admin switches, registries) | The handler's bytecode | Whatever those contracts return; legitimate when it is application state the creator chose, a trust assumption otherwise |
| Code destroyed in its creation transaction and redeployed at the same address (metamorphic) | Detected: fills revert `HandlerCodeChanged`; the owner closes and recovers | Nothing runs |
| EIP-7702 delegated account | Refused at creation | (Its key holder could swap the delegation, or rewrite its storage through another delegate and swap back, at any time) |

A code hash proves only that the bytes executing are the bytes that were readable at creation. Since EIP-6780 a deployed contract's code can change only by being destroyed in the transaction that created it and redeployed, and an EIP-7702 account's code is a pointer its key can change, so the pin and the delegated-account check together make one statement true without qualification: **the code a counterparty reads is the code that will run**. Any way that code's behaviour can change is then visible in it: a `delegatecall`, an admin setter, an external call. Whether that is acceptable is the creator's choice and the counterparty's judgement; Market keeps the choice permissionless.

The reference handlers in `examples/` have no owner, no proxy, no `delegatecall` and no setters. Their only changing inputs are those named in each order's config (tokens, NFT collections, the bid strategy and capital source) and their own per-order state, written only by that order's fills.

## Owner review

1. **LICENSE copyright holder.** Added as "Copyright (c) 2026 ripe0x", from the repository's Git identity and GitHub owner. Change it if the work should be attributed differently.
2. **Cheap sales restart the rising bid (D110).** Zero is now refused, but a 1 wei sale still restarts `RisingStrategy` at its start price. If a creator wants growth that cheap sales cannot interrupt, the strategy should restart relative to the quote at the time of sale, which needs the handler to record that quote. Keep as is for the example, or change?
3. **Core dependency (D016).** The core now imports OpenZeppelin `Clones`. Accept, or inline the bytecode template (about 20 lines of assembly)?
4. **Setup and maintenance of active orders now go through handlers (D003).** All four examples need nothing from the owner while active, so they are unaffected. A third-party order that needs the order itself to act after creation (grant an approval to a DEX, accept a two-step ownership transfer, claim an airdrop, vote) must have a handler that does it in a fill, or the owner closes and recreates the order. Accept this as the price of the stronger commitment?
5. **Security review findings and residual risks** in [SECURITY.md](SECURITY.md).
6. **Approvals to counterparty-owned orders (D205, 2026-11-06).** Any handler that pulls a filler's assets under an approval to the order lets the order's owner take them after closing. `NFTBid` avoids it by holding the approval itself. The examples `AcquisitionBid` and `TokenExchange` still use approvals to their orders; they are documented as unsafe for fillers who cannot approve and fill atomically, not changed. Decide whether to rewrite them on the `NFTBid` pattern or remove them, and whether the core should ever restrict an owner's post-close `execute`.
