# Decisions

Each entry records the question, the choice, the alternatives considered and why they lost. Status: **Baseline** (implemented and tested), **Open** (owner review recommended). Entries dated 2026-11-04 unless stated. On 2026-11-05 the owner reviewed the open decisions: D004 changed to clones, D006 and D009 were settled as below, and D003, D005, D007, D008 and D010 to D016 were confirmed. This log replaces the decision log of the earlier NFT selling product, which remains on the `claude/market-nft-implementation-d5c4ea` branch.

## Starting point

The earlier work was an NFT selling product: a shared escrow contract holding every listed NFT and bid budget, OpenSea Seaport fills through a zone, fixed protocol and executor fees, a small owner role for currencies and zones, a Next.js app and a keeper. It reached fork tests against real OpenSea offers. Lessons carried over: ETH refunds into EIP-7702 accounts can run out of gas or hit an account without `receive` (here they simply revert the filler's own fill); fee-on-transfer and false-returning tokens must be detected by balance change; and Foundry's via-IR build can cache `block.timestamp` within a test function, so tests use `skip()`.

Nothing else carried over. The new direction removes marketplace semantics, fees, the owner role and shared custody.

| D001 | Baseline | Market is an execution-agnostic protocol. A creation hook letting the policy validate or initialise was rejected as unnecessary: a policy validates its config at fill time and a creator can simulate first. |
| D006 | Baseline (revised 2026-11-05) | Execution rules are immutable; application state may change. | D009 | Baseline (revised 2026-11-05) | The core stays execution-agnostic and verifies nothing for fillers. An optional, stateless periphery contract, `FillVerifier`, lets any account that can batch calls atomically check its own receipt around its own fill. | Evaluated: contract fillers (`GuardedBuyer`, `Matcher` in `test/Compose.t.sol`) can already check anything inline, so they gain little. ### D006: what policy immutability can mean

The goal is that an order is a stable commitment to its execution rules while its application state (price over time, capital, an artwork's colours, a bid's history) changes as those rules allow. What the core can establish depends on what kind of contract the policy is:

| Policy | What the commitment fixes | What can still change behaviour |
| --- | --- | --- |
| Ordinary contract with no upgrade path | The exact bytecode that runs, for the order's life | Only what that bytecode reads: its own storage (written by its own rules) and contracts it calls, such as tokens or the strategy and capital source named in config |
| Upgradeable proxy | The proxy's bytecode, which does not change on upgrade | Everything: whoever controls the implementation pointer controls every bound order during fills |
| Policy that `delegatecall`s an external implementation | The policy's bytecode | Everything the delegate target does, and the target itself if it is chosen from storage |
| Policy that depends on mutable contracts (oracles, admin switches, registries) | The policy's bytecode | Whatever those contracts return; legitimate when it is application state the creator chose, a trust assumption otherwise |
| Code destroyed in its creation transaction and redeployed at the same address (metamorphic) | Detected: fills revert `PolicyCodeChanged`; the owner keeps recovery | Nothing runs |
| EIP-7702 delegated account | Refused at creation | (Its key holder could swap the delegation, or rewrite its storage through another delegate and swap back, at any time) |

A code hash proves only that the bytes executing are the bytes that were readable at creation. Since EIP-6780 a deployed contract's code can change only by being destroyed in the transaction that created it and redeployed, and an EIP-7702 account's code is a pointer its key can change, so the pin and the delegated-account check together make one statement true without qualification: **the code a counterparty reads is the code that will run**. Any way that code's behaviour can change is then visible in it: a `delegatecall`, an admin setter, an external call. Whether that is acceptable is the creator's choice and the counterparty's judgement; Market keeps the choice permissionless.

The reference policies in `examples/` have no owner, no proxy, no `delegatecall` and no setters. Their only changing inputs are those named in each order's config (tokens, NFT collections, the bid strategy and capital source) and their own per-order state, written only by that order's fills.

## Example design

| ID | Status | Decision | Alternatives and reasons |
| --- | --- | --- | --- |
| D101 | Baseline | Policies act only through the calling order, take only from `caller`, key state by `msg.sender` and build every call themselves. | These are what keep a shared policy from becoming shared authority. Listed for authors in the README. |
| D102 | Baseline | `DutchAuction` closes the order after a sale (about 22,000 gas). | Without closing, an NFT sent back to the order address would be for sale again at the end price. |
| D103 | Baseline | Payments to configured payees are pushed in the fill. A reverting payee blocks fills. | Pull payments need per-payee state in the policy. The creator chooses payees; `test_rejectingPayeeBlocksSale` documents the effect. |
| D104 | Baseline | `TokenExchange` measures payment as the payee's balance increase and delivery as the recipient's. | Trusting return values misses fee-on-transfer tokens and self-payment. Delivery checking was added after review finding F2. |
| D105 | Baseline | `PaintAction` paints, then resigns the painter role and closes the order. `Artwork` clears the painter on transfer. | Leaving the role with a closed order would still let the order's owner paint through it; resigning means nothing is left to reuse. Clearing on transfer makes offers from a previous owner stale. The artist's own power to repaint under `Artwork`'s rules is untouched; that is the artwork contract's design (D003). |
| D106 | Baseline | `AcquisitionBid` pays exactly the seller's asked price if it is above zero and within `min(strategy quote, maxPrice, capital)`, checks the recipient did not hold the token before and does after, then records the clearing price. | Paying the full current bid instead would let front-running reduce a seller's price silently; an explicit price either clears or reverts. The before-check stops self-delivery (`test_selfDeliveryRejected`). |
| D107 | Baseline | `CapitalPool` grants stream from zero at `rate` up to `cap`, can be revoked, and pay only filling orders. | A grant starting full would allow an immediate burst. The pool is example code, not part of Market. |
| D108 | Baseline | Bid strategies are separate `view` contracts chosen in config. | Shows an application can substitute pricing without touching Market or the policy (`test_substituteStrategyAndFunding`). |
| D109 | Baseline | `RisingStrategy` restarts at `resetBps` of the clearing price but never below `startPrice`. | Review finding F4: a sale at price 0 otherwise suppressed the bid to 0. Reusing `startPrice` as the floor needed no new parameter. |
| D110 | Baseline (2026-11-05) | `AcquisitionBid` rejects fills at price 0 (`ZeroPrice`). | Owner question: reject, or accept and leave pricing state unchanged. Rejecting is one line and keeps every recorded acquisition a paid purchase, so `count` and `lastPrice` mean what they say. Leaving state unchanged needs a branch and makes `count` include gifts. A holder who wants to give a token away can transfer it. Note: a sale at 1 wei is a real clearing price and still restarts `RisingStrategy` at `startPrice` (`test_cheapSaleRestartsAtStartPrice`); that is the strategy searching again, and each restart costs whoever forces it a token. See Owner review. |

## Owner review
